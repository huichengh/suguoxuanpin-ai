## ⚠️ 数据真实性声明

**本平台当前使用的全部数据均为基于公开行业数据构造的模拟演示数据，不代表华润苏果真实经营数据。**

所有页面在展示演示数据时都会标注来源，平台严格区分三类数据：

| 标记 | 含义 |
|------|------|
| `附件预置参考结果` | 项目附件 CSV 中直接给出的结果，平台原样保留、不做修改 |
| `系统实时重算结果` | 平台基于数据库原始数据、用当前算法参数重新计算的结果 |
| `模拟演示数据` / `基于公开行业数据构造` | 数据本身是构造的，不代表任何企业真实经营情况 |

平台不区分这两类结果，而是同时展示并解释差异来源（阈值、时间范围、聚合口径、标准化方式）。这是平台的数据治理能力之一。

关于品类数量的一处事实：品类表共 9 个，其中火锅食材与烘焙用品没有月度销售记录，
因此不进入健康度评分的对标域，界面显示为 7 个品类参与评分。平台不做数据摊派——
没有销售数据的品类不会被补一个估算值塞进排名。

## 多门店管理（v1.2 新增）

### 门店录入

支持录入任意数量的门店。**基础信息 + 画像数据 + 经营指标**三段式：

| 分组 | 字段 |
|------|------|
| 基础信息 | 门店名称、编码、城市、区县、商圈、门店类型、营业面积、数据来源 |
| 门店画像 | 3公里人口、居民/办公/学生/中老年占比、住宅/办公/学校 POI、消费能力、主要竞品、配送能力 |
| 经营指标（月） | 月销售额、月毛利额、毛利率、月销量、坪效、库存周转天数、在售SKU数、月缺货次数、会员销售占比、日均客流、综合健康度 |

**附件只有黄金海岸广场店一家的数据。** 平台在初始化时从 `category_sales.csv` 算出该店 2026-09 的
真实指标（月销售额 521,012 元、毛利额 108,981 元、毛利率 20.92%、健康度均值 55.09），
其余门店的指标必须人工录入或后续系统对接获取。

**平台不会为任何门店生成或推算经营数据。** 未填字段在对比中显示「待接入」，
不参与该店得分计算。

### 多门店对比

支持 2 家以上门店横向对比，输出：

1. **综合得分排名** —— 各维度标准化得分的算术平均
2. **11 个维度对比表** —— 含每家店的原值、标准化得分、最优门店
3. **门店能力雷达** —— 选取数据完整的维度做多店叠加
4. **差异分析** —— 按极差比排序，标注差异显著的维度（比值 ≥ 1.5）
5. **画像对比** —— 人口结构、POI、消费能力

**指标方向处理**（与品类健康度模型一致）：

| 类型 | 维度 | 处理 |
|------|------|------|
| 越高越好 | 销售额、毛利额、毛利率、销量、坪效、会员占比、客流、健康度 | 正向标准化 |
| 越低越好 | 库存周转天数、月缺货次数 | **逆向标准化** |
| 中性 | 在售SKU数 | 不参与排名 |
| 缺失 | 任意维度的空值 | 显示「待接入」，该店该维度不计分 |

数据不足的门店不进排名，并单独列出提示补录。

### 多门店可支撑的决策场景

- **定位差异化** —— 对比不同商圈门店的坪效、周转、客群结构差异
- **标杆复制** —— 识别领先门店，分析其领先维度并推广可复制动作
- **短板诊断** —— 定位某店在特定维度的显著落后（如坪效仅为最优店的 1/5）
- **品类调优** —— 结合客群结构差异差异化调整品类结构，支撑「千店千面」落地

## 3 分钟自动演示

**入口有两处**：
- 顶部工具栏常驻「▶ 3 分钟自动演示」按钮
- 驾驶舱的「一键 3 分钟自动演示」按钮

演示器挂在 `Layout` 层，**路由切换时不会卸载**。8 步自动轮播。

**每步时长由解说词长度决定，不是写死的秒数**：

```
停留秒数 = 解说词朗读时间 + 2.5 秒缓冲
朗读时间 ≈ 字数 ÷ 5.5 字/秒（rate=1.05 的中文 TTS 经验值）
```

实际播放时用 `SpeechSynthesisUtterance.onend` 拿到**真实语音时长**并校正，
所以不同机器的语速、语音引擎差异都不会影响演示节奏。
页面上会显示「实测语音 XXs ＋ 缓冲 2.5s ＝ 停留 XXs」，
语音播完后自动从「按字数估算」切换为「实测语音」。

单步限制在 10-38 秒之间，避免过短显得仓促或过长显得拖沓。

**可得字段**：销量、销售额、均价、成交笔数、连带率、关联强度（由 Apriori 回填）
**不可得字段**：毛利额、周转天数、坪效

附件的交易明细不含成本、库存与陈列面积字段，因此小类层**没有毛利、周转、坪效**。
平台的做法是：

- 数据库中这三个字段保持 `NULL`，代表「未接入」
- 小类比较自动降级为**两维模型**（销量 50% + 销售额 50%）
- 页面明确展示降级原因，并提示「上传 SKU 级数据后自动切回四维」
- **绝不用大类数据摊派到小类**

### 为什么小类比较用两维模型

大类是四维模型（销量30% + 毛利30% + 周转20% + 坪效20%）。
小类如果强行套用四维，就必须填入编造的毛利和周转数据。
平台选择降级为两维并说明原因，而不是造数据——这本身是数据治理能力的一部分。

在「数据中心」上传 SKU 级数据（含毛利率、库存周转天数、坪效）后，
`resolve_model()` 会自动检测到字段齐全并切回四维模型，无需改代码。

### ABC 分类

按累计销售额占比划分，替代 K-means 聚类：

| 类别 | 累计销售额 | 当前数据下数量 | 占比 | 策略 |
|------|-----------|--------------|------|------|
| A 核心商品 | 0-70% | 40 个 | 57.1% | 保障货源、安全库存、最佳陈列位 |
| B 次要商品 | 70-90% | 19 个 | 27.1% | 维持投入，关联陈列提升连带率 |
| C 长尾商品 | 90-100% | 11 个 | 15.7% | 缩减面积与订货，评估转线上专供 |

**为什么不用 K-means 聚类**：最初实现的是 K-means，但实测发现当前演示数据的
小类销量极差仅 3.2 倍、均价极差仅 1.13 倍，聚类分出的簇内部差异极小
（明星品 1338 件 vs 长尾品 1273 件），且「问题品」占了 58%，说服力不足。
ABC 分类基于累计贡献，结论稳定可解释，40/19/11 的分布也更符合商业直觉。

平台内置**数据区分度诊断**，每次分类自动计算极差比并如实展示局限。
当前数据下均价极差 1.13 倍（低于 2 倍判定线），页面会明确标注这一点。

### 货架空间优化

按「单位面积销售额」分配货架面积，引入平滑系数 α：

```
权重_i = (销售额_i / 总销售额)^α
面积_i = 总面积 × 权重_i / Σ权重
```

- α = 1.0：纯按销售额分配，头部集中
- α = 0.65：默认，兼顾产出与长尾（推荐）
- α = 0.3：接近平均分配

另设最小占比下限（默认 0.5%），保证长尾商品有基本陈列面。
**下限必须可行**：70 个商品时 2% 下限会导致 n×min_share > 100% 而退化成平均分配，
所以代码里取 `min(min_share, 1/n × 0.5)`。

页面同时展示**贪心装箱对比**：纯贪心按销售额填满货架会挤掉长尾，
本模块的 α 平滑正是为了平衡产出效率与长尾覆盖。

## 核心算法

### 1. 品类健康度评分

```
综合得分 = 销量得分×0.30 + 毛利得分×0.30 + 周转得分×0.20 + 坪效得分×0.20
```

各指标标准化到 0-100。**关键点：库存周转天数越低越好，采用逆向标准化**（不能直接正向 Min-Max）。

| 得分区间 | 等级 | 星级 |
|----------|------|------|
| 85-100 | 优秀 | ★★★★★ |
| 70-84 | 良好 | ★★★★☆ |
| 55-69 | 一般 | ★★★☆☆ |
| 40-54 | 较差 | ★★☆☆☆ |
| 0-39 | 差 | ★☆☆☆☆ |

低于 55 分标记「需重点优化」。

### 2. Apriori 购物篮分析

默认参数：`min_support=0.02`、`min_confidence=0.50`、`min_lift=1.50`、`TopN=20`

**购物篮构建：`交易号 + 商品名称`**。当前演示数据中同一商品名称存在多个不同编码（编码高度离散），
按商品编码直接分析会得到无意义的规则。真实企业数据接入后 SKU 编码稳定，可在「高级设置」中切换。

实现：自研 Apriori（不依赖 mlxtend），用倒排索引 + 集合交集算支持度。
5000 笔交易篮 × 70 个商品项的运算从 22 秒降到 55 毫秒。

指标定义：
- `support(A→B) = P(A∩B)` —— 同时购买 A 和 B 的交易占比
- `confidence(A→B) = P(B|A) = support(A∩B) / support(A)`
- `lift(A→B) = P(A∩B) / (P(A)×P(B)) = confidence / support(B)` —— 提升度 > 1 表示正相关

> 提升度公式容易写错。如果写成 `confidence / support(A∩B)` 会得到 10+ 的异常值，
> 单元测试用构造数据（期望 1.5）能第一时间发现这个错误。

### 3. 需求预测

附件中的预测值为模拟结果（Prophet 标准输出格式），平台**原样展示并标注「模拟预测结果」**，
不为其标注任何预测精度（如 MAPE）。

「用移动平均模型重跑预测」按钮会用平台自己的算法基于历史数据实际计算。
由于历史数据仅 12 期（推荐 24-36 期），结果仅供趋势参考，平台会明确提示样本有限。

趋势分类：变化幅度超过 ±5% 为温和上涨/下降，±10% 为明显上涨/下降。

### 4. ABC 分类

按累计销售额占比 70/20/10 划分 A/B/C 三类。详见「小类层分析」章节。

### 5. 货架空间优化

权重 = 销售额^α 后归一化，α 控制集中程度。详见「小类层分析」章节。

## AI 选品助手

### 五项原则

1. **数据优先** —— 量化结论必须来自数据库与算法结果，信息不足时明确回答「当前数据不足以支持该结论」
2. **可解释** —— 每条建议说明依据、关键指标、最大风险、是否需人工确认
3. **AI辅助、人工决策** —— 不自动下采购订单、修改价格、淘汰供应商、删除商品
4. **区分真实与模拟数据** —— 演示数据必须标注
5. **不混淆附件参考与实时重算** —— 并解释差异来源

### 标准回答模板

```
【结论】       一句话给出判断
【关键数据依据】 3-5 项最重要的数据
【分析】       销量/毛利/周转/坪效/缺货/关联/趋势的解读
【建议】       具体可执行动作
【风险与限制】 数据来源与局限
【决策状态】   AI建议 / 需人工确认 / 待审批
```

## 审批机制

| 等级 | 类型 | 是否需审批 | 示例 |
|------|------|-----------|------|
| Level 1 | 信息提示 | 否 | 风险预警提示、数据质量提示 |
| Level 2 | 经营建议 | 否（可采纳/驳回） | 关联陈列调整、备货量调整 |
| Level 3 | 高影响建议 | **必须** | SKU 退出、大规模精简、供应商调整、重大补货、价格调整 |

## 数据不足时的行为

平台遵循「不生成假结果」原则：

| 缺失数据 | 平台行为 |
|----------|----------|
| SKU 级经营指标 | 显示「当前数据不足以进行完整SKU量化评价」并引导上传 |
| 会员 RFM 数据 | 显示「当前无法完成 RFM 客群分层」 |
| 门店 POI / 人口数据 | 显示「千店千面模块待接入门店周边数据」，不编造人口数量 |
| 历史数据 < 12 期 | 显示「历史数据量有限，预测结果仅供趋势参考」 |
| 新品同类 SKU 表现 | 只给「高潜力/中等潜力/谨慎试销」等级，不输出成功概率 |

## 部署说明

线上部署为单端口 HTTP 服务，后端同时承担接口与页面托管：

```
server.py                  启动入口，读 PORT 环境变量、绑定 0.0.0.0
backend/static/            前端构建产物（由 frontend/dist 复制而来）
backend/requirements.txt   依赖清单
```

两处实现细节值得说明，都是为适配部署环境而做的：

**令牌校验不依赖 PyJWT。** 平台的令牌签发与校验用标准库 `hmac` + `hashlib` 手工实现
HS256，原因是在部分部署环境下 PyJWT 会出现「签名完全正确但校验抛
`InvalidSignatureError`」的情况，表现为登录成功后所有业务接口一律 401。
手工实现只依赖标准库，行为可预期。`PyJWT` 版本已钉死为 `2.9.0`。

**令牌同时放在两个请求头。** 前端会同时发送 `Authorization` 与 `X-Auth-Token`：

| 请求头 | 用途 |
|--------|------|
| `Authorization` | 标准做法，本地与直连部署时使用 |
| `X-Auth-Token` | 自定义头，兜底 |

原因是部分网关会改写 `Authorization` 头（向其中追加自己的凭据），
使服务端截取到的令牌被污染而验签失败；自定义头不受影响。
服务端优先读 `X-Auth-Token`，缺失时回退到 `Authorization`，
两者都失败时再尝试从被改写的头中枚举候选并逐一验签。
